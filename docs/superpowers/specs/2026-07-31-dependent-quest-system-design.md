# Dependent Quest System Design

## Objective

Make quests reliable end to end: discoverable from generated NPCs, gated by
prerequisites, progressed only after acceptance, completable for every goal
type, persisted across save/load, and validated across multiple world seeds.

## Current Defects

- `CompleteQuest` only handles `RetrieveItemGoal`; `kill_rats` can become ready
  but cannot complete or grant rewards.
- Quest state is not saved. Loading a game silently loses all active and
  completed quests.
- Kill counts include enemies defeated before accepting the quest.
- Quest definitions cannot express prerequisites or follow-up quests.
- The spawn village does not guarantee enough eligible generic buildings for
  both quest givers across all seeds.
- Goal evaluation, dialogue updates, item consumption, and rewards are split
  between `QuestSystem` and `ConversationSystem`, with duplicated branching.

## Chosen Approach

Use declarative quest definitions plus a small persisted runtime state.

This is preferable to:

1. **Minimal patching:** adding prerequisite checks to the existing status map
   would be smaller, but would preserve duplicated completion code, pre-accept
   kill counting, and weak persistence.
2. **Event-sourced quest engine:** deriving all quest state from gameplay events
   would be flexible, but is disproportionate to the game's current size and
   save model.

## Domain Model

`Quest` gains:

- `prerequisiteQuestIds: Set[String] = Set.empty`
- `followUpQuestId: Option[String] = None`

`GameState.quests` becomes `Map[String, QuestState]`, where:

- `status: QuestStatus`
- `progressBaseline: Int`

The baseline records relevant progress when a quest is accepted. For kill
quests it is the number of matching kills already in `EventMemory`, so only
later kills count. Item quests use zero because their goal is intentionally
based on current inventory.

Repository validation rejects invalid quest data during startup/tests:

- map key must equal `Quest.id`
- all prerequisite and follow-up IDs must exist
- dependency graph must be acyclic
- goal amounts must be positive
- rewards must be non-negative
- follow-up quests must declare the current quest as a prerequisite

## Quest Lifecycle

A central `QuestSystem` API owns lifecycle behavior:

- `availability(gameState, questId)` returns locked, available, active,
  completed, or failed.
- `acceptQuest` validates the quest exists and all prerequisites are completed,
  captures the progress baseline, updates state, and returns a user-facing
  message.
- `progress` and `isGoalSatisfied` evaluate any supported goal.
- `completeQuest` revalidates the active state and goal, consumes required
  items when appropriate, awards coins and XP exactly once, marks completion,
  and returns follow-up dialogue choices.

`ConversationSystem` delegates to these APIs rather than implementing
goal-specific rules itself. Attempting to accept a locked quest leaves state
unchanged and reports the titles of incomplete prerequisites. Locked quests
remain visible through their existing NPC conversation choices.

The first implementation retains the two existing goal types:

- `RetrieveItemGoal`
- `KillEnemyGoal`

Both use the same completion path. Additional goal types can be added by
extending the evaluator and completion effect without changing conversation
handling.

## Quest Chain and Content

The initial chain is:

1. `retrieve_statue` — no prerequisites, given by the Elder.
2. `kill_rats` — requires `retrieve_statue`, given by Quest Giver.
3. `slime_cleanup` — requires `kill_rats`, given by Quest Giver.
4. `snake_hunt` — requires `slime_cleanup`, given by Quest Giver.

Each completion dialogue offers the next quest when the same NPC owns the
follow-up. When the giver differs, the next giver's existing visible choice
becomes acceptable after prerequisites are met.

Enemy requirements use types already generated by dungeon depth:

- rats for `kill_rats`
- slimes/slimelets for `slime_cleanup`
- snakes for `snake_hunt`

Descriptions direct the player to dungeons rather than claiming enemies are
immediately beside the village.

## World Generation

Spawn villages generate four to six buildings with these mandatory types:

- farmland
- three generic buildings

At most one generic building contains the player spawn, leaving two guaranteed
eligible quest-giver buildings. The Elder and Quest Giver therefore spawn for
every tested seed without overlapping the player.

The existing eastern-dungeon `GoldenStatue` requirement remains. Seed tests
verify:

- both quest givers exist exactly once
- the Golden Statue exists in the eastern required dungeon
- enough rat, slime/slimelet, and snake enemies exist to satisfy the chain
- generation remains deterministic for identical seeds

If enemy-count tests reveal a type is not guaranteed, generation will add a
small declarative required-enemy set to the appropriate dungeon configuration
rather than weakening the quest.

## Persistence

`PersistedGameState` gains a version-tolerant quest-state map with an empty
default. Save/load round trips preserve status and baseline. Old saves that
lack this field load with no accepted quests, matching their prior effective
behavior.

## UI

The character screen continues to show active and completed quests using the
runtime status.

Map markers remain goal-specific:

- retrieve-item quests point to the item, then the giver
- kill quests point to the giver only when their post-accept requirement is met

Locked quests do not appear as active markers.

## Reliability and Error Handling

- Unknown quest IDs produce a clear message and no state mutation.
- Locked, duplicate, already completed, and unsatisfied completion attempts are
  idempotent and grant no rewards.
- Missing quest-giver entities do not crash updates; quest progress remains
  intact and can be completed once the giver exists.
- Rewards are emitted only on the active-to-completed transition.
- Repository validation makes malformed static quest data fail tests early.

## Delivery Chunks

1. **Lifecycle foundation:** repository validation, prerequisites,
   `QuestState`, centralized acceptance/completion, kill completion, tests.
2. **Persistence:** save/load quest runtime state and backward-compatible tests.
3. **Quest chain:** add follow-ups and dependent quest definitions/NPC dialogue.
4. **World guarantees:** deterministic quest-giver buildings and multi-seed
   content tests; add required enemy generation only if tests prove necessary.
5. **UI and regression:** update status consumers and markers, then run compile,
   full tests, coverage analysis, and web build.

Each chunk is committed and pushed independently after its targeted and full
tests pass.
